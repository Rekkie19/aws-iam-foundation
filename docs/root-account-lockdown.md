# Management-account root lockdown

Manual checklist for the AWS account that will become the Organizations management account. Complete it before any Terraform milestone. Root credentials never go into Terraform, GitHub Actions, a pull request, or this repository.

Do not commit evidence that this list is done. Do not commit screenshots, account IDs, contact addresses, alarm names, or topic ARNs. Tick the boxes in your own notes.

Official references:

- [Root user best practices](https://docs.aws.amazon.com/IAM/latest/UserGuide/root-user-best-practices.html)
- [Tasks that require root user credentials](https://docs.aws.amazon.com/IAM/latest/UserGuide/id_root-user.html#root-user-tasks)
- [Multi-factor authentication for the root user](https://docs.aws.amazon.com/IAM/latest/UserGuide/enable-mfa-for-root.html)
- [Enable a passkey or security key for the root user](https://docs.aws.amazon.com/IAM/latest/UserGuide/enable-fido-mfa-for-root.html)
- [Alternate contacts](https://docs.aws.amazon.com/accounts/latest/reference/manage-acct-update-contact-alternate.html)
- [CloudWatch billing alarm](https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/monitor_estimated_charges_with_cloudwatch.html)

Sign in as the root user only while you work through this list, then sign out. Prefer a private browser session. Confirm the account name in the console before you change credentials, so you lock down the account you mean to keep.

## 1. Strong unique password

- [ ] Replace the root password with a unique passphrase generated by a password manager.
- [ ] The password is not reused on any other site, and it is not the account name or the root email address.
- [ ] AWS requires 8 to 128 characters and at least three of: uppercase, lowercase, numbers, and symbols. Use a passphrase well above that minimum.
- [ ] The password manager has its own MFA. The root password is not stored in this repository, in GitHub, in a browser profile on a shared computer, or in a note that depends on the same AWS account.

Change it from the root security credentials page: [Change the root user password](https://docs.aws.amazon.com/IAM/latest/UserGuide/root-user-password.html).

## 2. Recovery channels, before MFA

AWS can use the root email and the account phone number to recover a lost MFA device. Update those before you change MFA.

- [ ] The root email is an address you control. A group mailbox is better than a personal inbox that only one person can open.
- [ ] The account phone number is current, and you can receive calls or texts to it.
- [ ] When a second person exists, one person does not control both the mailbox and the phone number.
- [ ] The primary account contact (name, address, phone) is current.

## 3. Phishing-resistant MFA

Register passkeys or FIDO2 security keys. SMS is not acceptable. A virtual TOTP app is not the target; it is phishing-able and it is a single phone.

AWS allows up to eight MFA devices on root. Register more than one so a lost key is not an account recovery.

- [ ] At least two phishing-resistant factors are registered: two hardware security keys, or one hardware key and a passkey stored separately from the root password.
- [ ] The devices are kept in different places. One can live with you. One stays offline.
- [ ] You signed out and signed back in with each new factor, and the console accepted it.
- [ ] Any weaker factor (SMS or virtual TOTP) was removed only after a phishing-resistant factor worked.
- [ ] Device names in the console do not embed secrets. "primary-key" and "backup-key" are enough.

Console path: root user, **Security credentials**, **Assign MFA device**, **Passkey or security key**. Details: [Enable a passkey or security key for the root user](https://docs.aws.amazon.com/IAM/latest/UserGuide/enable-fido-mfa-for-root.html).

If you are the only operator, you still keep two factors in two places. Split knowledge (one person holds the password, another holds MFA) applies when a second operator exists.

## 4. Delete root access keys

Root does not get access keys, CloudFront key pairs, or X.509 signing certificates.

- [ ] On **My security credentials**, the access keys section is empty. If a key exists, disable it, confirm nothing uses it, then delete it.
- [ ] No CloudFront key pairs are listed.
- [ ] No X.509 certificates are listed.
- [ ] You did not create a replacement key "for Terraform" or "for the CLI". Later milestones use Identity Center and GitHub OIDC.

## 5. Alternate contacts

Add billing, operations, and security contacts so AWS can reach a monitored mailbox when the root mailbox is missed. Contacts can be distribution lists. They do not need to be the same person.

- [ ] Billing alternate contact is set.
- [ ] Operations alternate contact is set.
- [ ] Security alternate contact is set.
- [ ] Each address is monitored, and the security contact is not a mailbox that nobody reads.

Console path: account menu, **Account**, **Alternate contacts**. See [Update the alternate contacts for your AWS account](https://docs.aws.amazon.com/accounts/latest/reference/manage-acct-update-contact-alternate.html).

## 6. Billing alarm

Create an alarm now, before Terraform exists, so a mistake during bootstrap is visible. Milestone 10 codifies the same control. Leave the manual alarm in place until that code has replaced it.

Estimated-charges metrics are published in **us-east-1**, and only after billing alerts are enabled.

- [ ] In Billing preferences, **Receive Billing Alerts** is on.
- [ ] In CloudWatch in **us-east-1**, an alarm watches `AWS/Billing` / `EstimatedCharges` for currency `USD`.
- [ ] The threshold is low enough that you would notice it on a new foundation account. A monthly estimate around 10 USD is a reasonable starting point; raise it when you know the real baseline.
- [ ] The alarm notifies an email address you monitor, and the subscription is confirmed.
- [ ] The topic, alarm, and email are not copied into this repository.

See [Create a billing alarm](https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/monitor_estimated_charges_with_cloudwatch.html).

## 7. Never use root day to day

- [ ] You are signed out of the root session.
- [ ] Day-to-day administration waits for IAM Identity Center (roadmap milestone 6). Until then, root is used only to finish this checklist and to perform a task that [requires the root user](https://docs.aws.amazon.com/IAM/latest/UserGuide/id_root-user.html#root-user-tasks).
- [ ] Terraform applies do not use root.
- [ ] Nobody else has the root password, the MFA devices, or a copy of an access key.
- [ ] You have a personal reminder to treat a root sign-in as an exception. Organization CloudTrail and a root-activity alert arrive with milestone 10; until then, the console's recent root activity is the check.

## After the organization exists

Member accounts have their own root users. When Organizations is in place, enable [centralized root access](https://docs.aws.amazon.com/IAM/latest/UserGuide/id_root-enable-root-access.html) and remove member-account root credentials (password, keys, signing certificates, and MFA) so those roots cannot sign in. Where a member root must remain, repeat this checklist for that account. An SCP that limits root use in member accounts to the few actions root alone can perform belongs with the guardrail milestone.

Do not start that work from this document. It depends on the organization milestone.
